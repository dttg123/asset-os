ASSET OS 장기운영 QA 설계·실행 기준 FINAL v3
작성일: 2026-09-28 (KST)
개정 방향: 개인용 앱 / 최초 구축부터 30~35년 운영 전제
최종 적용 원칙: 핵심 안전성은 완성형으로 구축하고 기업용 과잉 QA는 제외
권장 저장 위치: asset-os/docs/QA_POLICY.txt
대상: Asset OS 개인 자산관리 모바일 웹앱

======================================================================
1. 문서 목적
======================================================================

이 문서는 Asset OS를 수정할 때 어떤 QA를 어느 강도로 실행해야 하는지 정한다.
목표는 사용자가 작은 수정 때마다 앱 전체를 수동 검사하지 않아도 되게 만드는 것이다.

이 앱은 개인 1인이 장기간 사용하는 금융 앱이다.
따라서 기업용 QA 조직이나 과도한 인프라는 만들지 않지만 다음은 엄격히 검증한다.

- 금융 계산 정확성
- 사용자 데이터 보존
- 백업·복원 호환성
- KIS 읽기 연동과 중복 방지
- 휴대폰·PC 동시 저장 충돌
- 인증·RLS·비밀정보 보호
- Galaxy 모바일 화면과 PWA 업데이트

QA의 기본 원칙:
- TypeScript 통과는 QA의 시작이지 완료가 아니다.
- 자동 테스트가 없는 새 핵심 기능은 완료로 처리하지 않는다.
- 테스트는 실제 배포 소스를 대상으로 해야 한다.
- 운영 사용자 데이터를 자동 QA에 사용하지 않는다.
- QA 데이터는 격리하고 종료 후 0건으로 정리한다.
- 실제로 하지 않은 실기기·실계정 QA를 했다고 기록하지 않는다.
- 재시도 후 우연히 통과한 테스트는 정상 PASS로 숨기지 않는다.
- 작은 변경에는 타깃 QA, 고위험 변경과 큰 배포에는 전체 QA를 실행한다.

======================================================================
1-A. 처음부터 구축할 장기 QA 기반
======================================================================

장기 QA는 앱을 완성한 뒤 마지막에 붙이는 작업이 아니다.
아래 구조는 초기 TypeScript 전환·원장 정리 단계부터 같이 구축한다.
처음부터 데이터 수천 건을 손으로 만드는 것이 아니라, 작은 기준 데이터와 재현 가능한
생성기를 먼저 만들어 기능과 데이터가 늘어도 QA 비용이 폭증하지 않게 한다.

[논리적 분류 — 전부 별도 파일·폴더로 만들 필요는 없음]

tests/
- unit/                 계산 함수·검증 함수
- integration/          저장소·마이그레이션·API 경계
- e2e/                  Playwright 사용자 흐름
- fixtures/golden/      독립 검산한 불변 계산 사례
- fixtures/legacy/      과거 schema·백업 포맷
- fixtures/api/kis/     비식별 KIS 성공·실패 응답
- fixtures/bugs/        실제 발견 버그 재현 자료
- factories/            계좌·종목·거래 기본 생성기
- generators/           1·5·10·30년 seed 기반 생성기
- visual/               기준 화면과 승인 기록

초기에는 관련 항목을 한 파일에 묶어도 된다. 파일이 지나치게 길어지거나 변경 이유가
달라질 때만 분리한다. 테스트만을 위해 수십 개의 빈 폴더·빈 파일을 만들지 않는다.
실제 폴더명은 저장소 구조에 맞춰 조정할 수 있지만 역할과 데이터 성격은 섞지 않는다.
QA 파일은 프로덕션 번들에 포함하지 않는다.

[권장 실제 규모]
- 처음 완성 시 테스트·fixture·설정 전체 약 15~25개 파일
- 계산·저장·동기화·E2E처럼 변경 이유가 다른 영역만 분리
- 테스트 1개당 파일 1개 또는 화면 1개당 파일 1개 방식은 금지
- 버그 사례는 가능하면 기존 도메인 테스트에 추가하고, 복잡할 때만 별도 파일 생성
- 파일 개수 자체를 품질 목표로 사용하지 않는다.

[세 가지 QA 데이터]

1) 불변 fixture
- 손으로 독립 검산한 금융 계산 정답
- 한번 발생한 버그의 최소 재현 데이터
- KIS 중복·부분 실패·오류 응답
- 손상 백업과 경계 날짜 데이터
- 의미가 바뀌지 않는 한 기존 값을 수정하지 않는다.

2) 버전 fixture
- schema-v1, schema-v2처럼 원본 형식을 그대로 보존한다.
- 계산 정책·ISA 정책·백업 포맷이 바뀌면 기존 파일을 덮지 않고 새 버전을 추가한다.
- 모든 지원 버전은 최신 버전으로 마이그레이션된 뒤 같은 핵심 합계를 내야 한다.

3) 생성 데이터
- 장기간 거래·납입·시세는 generator가 만든다.
- seed, 시작일, 기간, 규모, 정책 버전을 기록한다.
- 같은 seed는 언제든 같은 결과를 만들어야 한다.
- 생성 결과 파일을 대량으로 저장하지 않고 실패 재현에 필요한 최소 seed만 보존한다.

[처음 만들 최소 기준 세트]

- golden 계산 15~25개
- 대표 사용자 여정 8~12개
- KIS 성공·401·429·500·부분 성공·빈 응답·중복 응답 fixture
- 과거 백업/스키마 최소 1개씩과 손상 백업 2개
- 1년·5년·10년·30년 generator 각 1개 프로필
- 데이터 0건·일반·큰 금액·음수·긴 이름 시각 상태
- 실제로 수정한 버그부터 bugs/에 계속 누적

숫자는 목표치가 아니라 시작 범위다. 같은 의미의 데이터를 중복해서 늘리지 않는다.

======================================================================
1-B. 변경할 때 QA 데이터를 유지하는 원칙
======================================================================

모든 기능 수정 때 모든 fixture를 바꾸지 않는다.

- UI 배치 변경: 계산 fixture는 수정하지 않고 시각 기준만 의도 확인 후 갱신한다.
- 내부 리팩터링: 기존 fixture와 기대값을 바꾸지 않는다. 전후 결과 동일성이 목적이다.
- 새 기능: 해당 기능의 factory 옵션과 대표 시나리오만 추가한다.
- 버그 수정: 버그를 재현하는 최소 fixture를 먼저 만들고 수정 후 영구 보존한다.
- 스키마 변경: 과거 fixture는 그대로 두고 새 schema fixture와 마이그레이션 테스트를 추가한다.
- 공식 계산정책 변경: 과거 정책 결과를 보존하고 적용일이 있는 새 정책 버전을 추가한다.
- 기대값 변경: 코드 결과를 복사하지 말고 손계산·독립 계산표·공식 규칙으로 다시 검산한다.

fixture 대량 수정이 발생하면 먼저 설계 문제를 의심한다.
공통 기본값은 factory 한 곳에서 관리하고 테스트마다 중요한 값만 명시한다.
단, golden·legacy·bugs fixture는 공통 factory 변경으로 몰래 바뀌지 않게 고정한다.

======================================================================
1-C. 30년 호환성을 위한 영구 계약
======================================================================

다음은 화면 구현보다 오래 유지되는 Asset OS의 데이터 계약이다.

- 모든 영구 데이터에 schemaVersion을 둔다.
- 금액·수량·날짜·통화의 저장 형식을 문서화한다.
- 원본 거래는 파생 합계와 분리하고, 합계는 언제든 다시 계산할 수 있게 한다.
- 마이그레이션은 v1→v2→v3처럼 순차 경로와 최신 직행 결과를 모두 검증한다.
- 이미 적용한 마이그레이션을 다시 실행해도 데이터가 중복·손실되지 않아야 한다.
- 백업에는 앱 버전·schemaVersion·생성일·무결성 정보를 포함한다.
- 최소 한 개의 오래된 실제 형식 비식별 백업을 버전별 회귀 자산으로 보존한다.
- 구버전 백업을 읽지 못하게 할 때는 자동 변환 또는 명확한 내보내기 절차가 있어야 한다.
- Node·TypeScript·브라우저·DB가 바뀌어도 같은 입력의 금융 결과는 동일해야 한다.
- 정책이 달라진 경우에는 오류가 아니라 정책 버전 차이로 설명 가능해야 한다.

[호환성 매트릭스]

정식 배포 전 최소 확인:
- 이전 운영 버전 저장 데이터 → 새 앱
- 이전 백업 포맷 → 새 앱 복원
- 새 앱 백업 → 같은 버전 재복원
- 오프라인 구버전 PWA → 온라인 신버전
- 휴대폰에서 만든 데이터 → PC 세션, 그리고 반대 방향

======================================================================
1-D. 장기 시뮬레이션의 합격 조건
======================================================================

단순히 30년 데이터가 화면에 뜨면 PASS가 아니다. 다음 불변식을 검사한다.

- 원장 합계 = 계좌별 합계의 합 = 통합 화면 합계
- 동일 데이터를 저장·복원·마이그레이션해도 핵심 합계가 동일
- 거래를 추가했다 삭제하면 추가 전 상태와 동일
- 중복 ID·중복 요청은 합계를 두 번 늘리지 않음
- 날짜 정렬이 입력 순서나 API 응답 순서에 좌우되지 않음
- NaN·Infinity·유실된 통화·음수 불가 수량이 없음
- 30년 생성 데이터를 다시 생성해도 같은 해시·요약 결과
- 데이터 증가에 따라 저장·복원·그래프가 실사용 불가능하게 급격히 느려지지 않음
- 실패 시 어느 seed·연도·계정·거래에서 깨졌는지 바로 재현 가능

성능은 기업용 동시접속 부하가 아니라 개인 실사용 기준으로 본다.
Galaxy S25 Ultra에서 핵심 화면 진입·저장·복원이 체감상 멈추지 않아야 하며,
구체적인 시간 기준은 현재 정상 버전의 기준값을 기록한 뒤 퇴행 여부로 판단한다.

======================================================================
1-E. 구축 순서와 실행 주기
======================================================================

[최초 구축]
1) 계산 로직을 UI에서 분리하고 unit 테스트 가능하게 만든다.
2) schemaVersion과 migration runner를 고정한다.
3) golden·legacy·API fixture를 만든다.
4) factory와 고정 seed generator를 만든다.
5) 핵심 Playwright 흐름과 백업 왕복을 자동화한다.
6) CI에서 Q0/Q1을 자동 실행하고 Q2/Q3는 조건부 실행한다.

[실행 주기]
- 코드 저장/PR: Q0
- 화면·기능 완료: 관련 Q1
- 계산·저장·KIS·권한 변경: Q2
- 정식 큰 배포·스키마 메이저 변경: Q3와 30~35년 시뮬레이션
- 매월 또는 중요 데이터 누적 후: 백업 실복원 1회
- 분기 또는 주요 의존성 변경 전: 전체 회귀와 PWA 업데이트 확인
- 연 1회: 오래된 백업 복원, 복구 문서, 의존성·런타임 지원상태 점검

정기 주기는 개인 앱에 맞춘 권장선이다. 변경이 없으면 의미 없는 반복은 하지 않는다.

======================================================================
1-F. 최종 실행 프로필 — 매번 전부 돌리지 않는다
======================================================================

테스트에는 @smoke, @core, @slow, @external 성격을 표시한다.

[FAST — 평소 수정]
- 타입·린트·변경 영역 단위 테스트
- 관련 smoke E2E
- 외부 실계정 호출 없음

[CORE — 기능 완료·PR·배포 후보]
- 금융 계산, 저장, 마이그레이션, 백업 왕복
- Chromium 모바일/데스크톱 핵심 E2E
- 비식별 KIS fixture
- 실패 시 trace와 화면만 보존

[FULL — 계산·스키마·동기화 변경]
- property-based 테스트
- 충돌·오프라인·RLS·서버 함수
- 1·5·10년 생성 데이터
- 핵심 화면 시각 회귀

[RELEASE — 큰 배포]
- 30~35년 생성 데이터
- 구버전 PWA→신버전
- 실제 Galaxy S25 Ultra
- 실제 KIS 읽기 전용 대표 조회
- 백업 실복원과 롤백 확인

Playwright 재시도는 진단용 1회까지만 사용하고 첫 실패를 숨기지 않는다.
trace는 모든 성공 테스트에 남기지 않고 실패 또는 첫 재시도에만 남긴다.

======================================================================
1-G. 개인 앱에 맞춘 축소 확정안
======================================================================

- 상시 브라우저는 Chromium 모바일·데스크톱만 사용한다.
- Firefox·WebKit은 해당 브라우저 사용 계획이 생기거나 호환성 변경 때만 확인한다.
- 시각 회귀는 통합 홈, 계좌 핵심 화면, 입력창, 백업/복원, 오류 상태에 한정한다.
- 모든 픽셀 차이를 배포 차단하지 않고 금액 잘림·버튼 가림·그래프 오류를 우선한다.
- 코드 전체 100% 커버리지는 목표로 삼지 않는다.
- 계산·마이그레이션·중복 방지·권한처럼 손실 위험 영역의 미검증 분기만 우선 보완한다.
- mutation testing, 대규모 부하, 다지역 장애복구, 24시간 관제는 도입하지 않는다.
- 실제 KIS 호출은 매 QA마다 하지 않고 연동 변경·큰 배포·장애 의심 때만 최소 실행한다.
- 새 기능과 관련 없는 golden·legacy·bugs fixture는 수정하지 않는다.

======================================================================
1-H. 런타임·도구의 30년 교체 정책
======================================================================

Node 24와 TypeScript 7은 2026년의 개발 기준이지 30년 동안 고정할 버전이 아니다.
Node 24 LTS의 공식 지원 예정은 2028년 4월 말까지이므로 그 전에 후속 활성 LTS 전환을 검토한다.

- package.json engines, 버전 파일, lockfile로 현재 기준 버전을 고정한다.
- 활성 지원 중에는 보안·패치 버전을 정기 반영한다.
- Node 메이저는 지원 종료 전에 다음 활성 LTS로 이동한다.
- TypeScript·Vitest·Playwright 메이저 변경은 별도 브랜치에서 전체 회귀 후 반영한다.
- 런타임 교체 전후 동일 fixture의 핵심 금융 요약 해시를 비교한다.
- 업그레이드 때문에 금융 기대값을 일괄 갱신하지 않는다.
- 오래된 의존성을 억지로 고정하는 것보다 작은 주기 업그레이드를 우선한다.

1-I. 백업 보존과 복구 최종선
======================================================================

개인 금융 데이터는 최소 두 종류의 독립 사본을 유지하고 가능하면 3-2-1에 가깝게 구성한다.

- 운영 데이터 1개
- 자동 클라우드 백업 1개
- 사용자가 내려받은 암호화 또는 안전 보관 백업 1개
- 자동 백업은 최근 세대를 순환 보존하되 사용자 지정 중요 백업은 자동 삭제하지 않는다.
- 백업 생성 성공이 아니라 실제 복원 성공으로 검증한다.
- 복원 시험은 격리된 QA 저장소에서 하고 운영 데이터를 덮지 않는다.
- 토큰·시크릿·세션·전체 계좌번호는 백업과 테스트 증빙에서 제외한다.

1-J. 모바일 기본 사용성·접근성 QA
======================================================================

개인 앱이므로 인증 심사 수준의 접근성 프로젝트는 하지 않는다. 다만 실사용 오류를 줄이는
기본 검사는 유지한다.

- 입력 필드의 보이는 라벨과 오류 안내
- 저장 성공·실패·동기화 상태 메시지
- 확대 글꼴에서 금액·버튼 잘림
- 터치 대상 간격과 잘못 누르기 쉬운 삭제 버튼
- 색상만으로 수익·손실·선택 상태를 구분하지 않음
- 모바일 키보드·뒤로가기·화면 회전 뒤 상태 보존

======================================================================
4. Playwright 핵심 사용자 흐름
======================================================================

다음 흐름은 자동화 대상이다.

1) 첫 실행 → 로그인 → 홈 진입
2) 수입 입력 → 소비 입력 → 가용현금 변화 확인
3) ISA 매수 → 수정 → 매도 → 한도·잔고 확인
4) 연금저축 납입 → IRP 납입 → 통합 합계 확인
5) 과거 거래 추가 → 1년·3년·5년·전체 그래프 확인
6) KIS 갱신 → 성공·부분 실패·재시도 표시 확인
7) 백업 다운로드 → 초기 상태 → 복원 → 전체 합계 비교
8) 오프라인 입력 → 온라인 복귀 → 동기화
9) 두 세션 동시 저장 → 충돌 처리
10) 로그아웃 → 재로그인 → 데이터 유지

각 테스트는 독립된 저장소·세션·데이터를 사용한다.
한 테스트가 만든 상태에 다음 테스트가 의존하지 않는다.

======================================================================
5. 시각 회귀 대상
======================================================================

필수 화면:
- 통합 홈
- ISA
- 연금저축
- IRP
- 월·년 분석
- 자산분석 그래프
- 입력·수정 하단 시트
- 설정·백업·복원
- KIS 갱신 결과

필수 상태:
- 데이터 0건
- 일반 데이터
- 매우 큰 금액
- 음수 수익률
- 긴 종목명
- 다크·라이트 테마
- 오류·부분 성공 메시지

기준 스크린샷은 동일한 브라우저·OS 환경에서 생성한다.
시각 차이는 자동 승인하지 않고 변경 의도와 비교한 뒤 갱신한다.

======================================================================
6. 장기 QA 데이터 규칙
======================================================================

30~35년 QA는 큰 배포 전 Q3에서만 실행한다.
작은 기능마다 반복하지 않는다.

포함할 시나리오:
- 매월 현실적인 수입·소비·저축·투자
- ISA·연금저축·IRP 납입과 거래
- 미납월·추가납입·계좌 이동
- 상승·하락·장기간 횡보
- 월말·연말·윤년
- 정책 버전 변경
- KIS 일부 실패와 재시도
- 휴대폰·PC 충돌
- 백업·복원

자동 생성 데이터는 고정 seed를 기록해 같은 오류를 재현할 수 있게 한다.
핵심 경계구간은 실제 UI로 직접 입력·수정·삭제한다.
종료 후 QA 계정·DB·스토리지의 QA 데이터가 0건인지 확인한다.

======================================================================
7. 실패 증빙과 flaky 테스트 처리
======================================================================

자동 저장할 증빙:
- 실패 테스트명과 단계
- 앱 버전·커밋·schemaVersion
- 실패 화면 캡처
- Playwright trace
- 실패 시점 영상(실패한 테스트만)
- 콘솔 오류
- 민감정보를 제거한 네트워크 오류
- 테스트 데이터 seed

규칙:
- 비밀키·토큰·전체 계좌번호는 증빙에 남기지 않는다.
- 재시도는 원인 분석을 위한 최대 1회만 허용한다.
- 첫 시도 실패 후 재시도 성공은 flaky로 기록하고 배포 전에 원인을 확인한다.
- 타이머를 늘려 통과시키는 임시 해결은 금지한다.
- 실패 테스트를 skip 처리해 배포하지 않는다.

======================================================================
8. 배포 차단 기준
======================================================================

다음 중 하나라도 발생하면 배포하지 않는다.

- TypeScript·빌드·핵심 테스트 실패
- 금융 합계·ISA 한도·연금 집계 불일치
- 백업 복원 결과 불일치
- KIS 잔고 중복·누락 또는 토큰 노출
- 다른 사용자 데이터 접근 가능
- 클라우드 충돌의 무음 덮어쓰기
- 구버전 데이터 마이그레이션 실패
- Service Worker 혼합 버전
- 모바일 핵심 버튼 사용 불가
- 원인을 모르는 flaky 핵심 테스트
- QA 데이터가 운영 환경에 남음

10. 개인 앱 기준으로 하지 않을 과잉 QA
======================================================================

- 수십 종류 휴대폰 실기기 조합
- 수천 명 동시접속 부하 시험
- 24시간 유료 관제
- 모든 브라우저·운영체제 조합
- 의미 없는 전체 코드 100% 커버리지 숫자 맞추기
- 작은 문구 수정마다 30년 전체 QA
- 운영 데이터를 복제한 무분별한 테스트

핵심 결론:
Asset OS는 변경 위험에 따라 Q0~Q3를 선택한다. 평소에는 자동 타깃 QA가 반복 검사를 대신하고,
금융 계산·저장·KIS·권한 변경과 큰 배포에서만 강화 QA와 30~35년 최종 QA를 실행한다.
